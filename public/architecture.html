Daromadchi — Multi-Marketplace Seller Dashboard
Syncs orders, inventory, and stock across Uzum Market and Yandex Market. Web dashboard + Chrome Extension for seller analytics. Marketplace integrations are read-only by default; the one exception is the opt-in, per-shop Stock-sync mode, which writes only the stock quantity (ostatok) through a single audited writer after the seller consents. Auth via NextAuth (Auth.js) v5 — Credentials + bcrypt, optional Google OAuth, JWT sessions, email verification. Self-hosted on a Hetzner VPS (Finland / Helsinki).

Payment System — ATMOS Integration
Daromadchi uses ATMOS (Uzbek payment aggregator) for all subscription charges. Money is integer tiyin (1 so'm = 100 tiyin). Two card flows: UzCard/Humo (direct card-binding, 3-call token charge) and Visa/Mastercard (hosted binding via MPS). Amount is ALWAYS derived server-side from PLAN_PRICES_TIYIN — never trusted from the client. ATMOS has no native recurring, so auto-renewal is a custom cron that charges stored card tokens.

Subscription Lifecycle
A subscription tracks one seller's relationship with a paid plan. The subscription status determines what happens at renewal time and whether the seller keeps access. The users.plan column (what was paid) is the ONLY input to feature gating — never derived_tier.
Subscription State Machine
States and transitions for subscriptions.status
pending
Payment initiated, awaiting ATMOS
active
Paid and running
past_due
Renewal failed, grace period
cancelled
Seller cancelled, access to period end

Expired / downgraded

pending→failedPayment fails or ATMOS config error

active→cancelledSeller cancels (cancelPlan) — keeps access to period end
active→past_dueRenewal charge fails

Price Change Notice Pipeline
Nobody is charged an amount they were not told about in advance. Every failure mode falls toward "keep charging what they agreed to."
1
STAGED
Operator sets pending_amount_tiyin + effective_date. Nothing charged. Must be an increase. Effective date ≥14 days away.
stagePriceChange()
→
2
NOTIFIED
Seller told via Telegram (uz/ru/en). Delivery recorded in pending_notified_at. Failed send = NOT recorded = increase never takes effect.
dispatchDuePriceNotices()
→
3
CHARGED
First renewal on/after effective date WHERE notice is ≥14 days old. Only then is pending promoted into agreed_amount_tiyin.
promotePendingAmount()
Safety invariant: An undelivered increase must never become chargeable by mere passage of time. If pending_notified_at is NULL, the pending amount is never charged — the seller keeps paying their agreed price.
Cancellation & Resume
What cancelPlan() and resumePlan() do and don't do
cancelPlan(userId)
Does: Sets ALL live subscriptions to status='cancelled', autorenew=false. Computes access_until = current_period_end. Records cancellation state.

Does NOT: Touch users.plan. Touch plan_expires_at. Remove card token. Refund anything. Immediately lock the seller out.

The seller keeps full access until the period they already paid for expires.
resumePlan(userId)
Does: Sets subscription back to status='active', autorenew=true. Only works while access_until > now (period still active).

Does NOT: Charge anything. Extend the period. Change the plan. This is an undo of the cancel, not a new purchase.

The next renewal will charge their stored card as usual.
